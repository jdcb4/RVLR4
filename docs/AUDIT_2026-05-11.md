# Audit & Recommendations — 2026-05-11

Snapshot audit of the codebase at `v0.14.1`. Findings combine a [`fallow`](https://docs.fallow.tools/) run, manual reading of the server + multiplayer client surface, and a review of project docs, CI, and security posture. **No code changes were made.** Recommendations are grouped by impact and effort so you can pick the next slice.

---

## TL;DR — top 5 next moves

1. **Validate every Socket.IO payload with Zod** at the handler boundary. The handlers currently coerce with `Number(...)` / `String(...)` and trust shape from `payload: { ready?: boolean }` type assertions. This contradicts `SECURITY.md` and `docs/ARCHITECTURE.md`, both of which list Socket.IO events as a validation surface.
2. **Add automated multiplayer tests.** Today the entire `server/` directory and `src/features/multiplayer/` have **zero unit/integration tests**; only the `MULTIPLAYER_QA.md` manual matrix exists. Even a single happy-path Socket.IO integration test would catch the kind of import-shape bugs fixed in 0.13.2 / 0.13.3 / 0.14.1.
3. **Refactor the three CRAP-critical files** (`ImposterMultiplayerView.tsx`, `RoomPage.tsx`, `socketHandlers.ts`). They are also the top churn hotspots — every release touches them, so cost of mistakes is high.
4. **Lock down CORS in production.** With `CLIENT_ORIGIN` unset in production today, the fallback resolves to `origin: true` (allow-all). That's fine for prototyping but should fail fast in prod.
5. **Add a graceful shutdown path** that disconnects sockets and stops the tickers on `SIGTERM`. Railway/Docker send `SIGTERM` on deploy; right now an in-progress match dies abruptly with no client-side hint.

## 1. Robustness — server / multiplayer

### 1a. Input validation (HIGH)

`server/socketHandlers.ts` registers ~30 `socket.on(...)` listeners. None of them validate the payload with Zod; they use TypeScript assertions like `payload: { teamIndex?: number }` and coerce with `Number(...)`. Examples:

- [`server\socketHandlers.ts:240`](server/socketHandlers.ts:240) — `Number(payload.teamCount)` accepts `NaN`, `Infinity`, or e.g. `"4; DROP …"` as a string.
- [`server\socketHandlers.ts:159`](server/socketHandlers.ts:159) — name slice is the only guard against payload abuse.
- Hat clue write-through (`lobby:hatSetClueCell`) trusts `clueIndex` from the wire.

`server/env.ts` already uses Zod nicely. Mirror that pattern with one schema per event in (e.g.) `server/socketSchemas.ts`, parsed in a thin wrapper:

```ts
const schemas = {
  "lobby:setReady": z.object({ ready: z.boolean() }),
  "lobby:hostSetTeamCount": z.object({ teamCount: z.number().int().min(2).max(4) }),
  // …
};
```

This also gives you a single place to apply per-event rate limits (see 1c).

### 1b. CORS fallback in production (MEDIUM)

[`server\index.ts:27`](server/index.ts:27):

```ts
const allowedOrigins =
  env.CLIENT_ORIGIN?.split(",")...
  ?? (env.NODE_ENV === "production" ? [] : ["http://localhost:5173"]);

const corsOrigin = allowedOrigins.length > 0 ? allowedOrigins : true;
```

If `CLIENT_ORIGIN` is unset in production, `allowedOrigins = []`, so `corsOrigin = true` (reflect any origin). Recommend: in production, refuse to start when `CLIENT_ORIGIN` is missing and `corsOrigin === true`. Fail fast at boot is consistent with the rest of `loadServerEnv`.

### 1c. No rate limits / abuse controls (MEDIUM)

Anyone with a room code can spam `lobby:setName`, `hat:skipClue`, room creation, etc. For a hobby app this is probably fine, but two cheap mitigations:

- `express-rate-limit` on `POST /api/rooms` and `POST /api/rooms/:code/join`.
- Per-socket token bucket on the high-frequency events (`lobby:hatSetClueCell`, `lobby:setName`).

### 1d. No graceful shutdown (MEDIUM)

`server/index.ts` listens on `0.0.0.0:PORT` but no `SIGTERM` / `SIGINT` handler. On Railway redeploy, Socket.IO connections are torn at the TCP layer; clients see a generic "disconnected" without the chance to flush state or show a friendly message. Add:

```ts
process.on("SIGTERM", () => {
  io.emit("server:shuttingDown");
  io.close(() => server.close());
});
```

### 1e. No structured observability (MEDIUM)

Only `MULTIPLAYER_DEBUG` `console.log` lines exist. For a "small self-hosted" target this is acceptable, but consider:

- A `pino` (or `console.*` wrapped) JSON logger so Railway log search works.
- Lightweight metrics: room count, players online, turns completed/min. Even a `/api/health` returning `{ rooms, sockets, version, uptime }` would help triage.
- An error sink — `socket.on("error")` and `io.engine.on("connection_error")` currently go nowhere.

### 1f. Replay / reconnect edge cases (LOW)

`RoomStore.authenticate` uses `player.secret !== args.secret` — a non-timing-safe compare. The secret is a 32-byte token, so collision risk is nil, but timing attacks are essentially free to attempt against a public Socket.IO endpoint. Use `crypto.timingSafeEqual` for defense in depth.

### 1g. In-memory state lifecycle (DOCUMENT)

Already a deliberate decision (`docs/DECISIONS.md` 2026-05-10). It's worth a one-pager in `docs/` that captures: maximum room cap (500), idle sweeper rules (30m/10m), restart kills active matches. That document is the place a future "do we need Redis?" conversation will start.

## 4. UX recommendations

These are aimed at "the multiplayer experience feels solid on phones around a real table." None require new dependencies.

### 4a. Connection-state feedback (HIGH)

`useRoomChannel` exposes `connected: boolean` and `bindError: string | null`, but most screens don't render either. Concrete asks:

- Persistent **"Reconnecting…" toast** at the top of `RoomPage` when `socket.disconnected` for >2s. Players currently see frozen UI and assume the game crashed.
- When the host drops mid-turn, every guest sees a stale timer until the server's ticker recovers. Show a "Waiting for host to reconnect" banner driven by `disconnectedAt`.
- Show "Server is restarting" copy when `server:shuttingDown` arrives (pairs with 1d).

### 4b. Room link UX (MED)

`shareUrl(code)` returns `/name?intent=join&code=ABC123`. Two improvements:

- Native [Web Share API](https://developer.mozilla.org/docs/Web/API/Web_Share_API) call when available — phones get the system share sheet (SMS, AirDrop, Signal) instead of copy/paste.
- Auto-focus the join code input on `/` for desktop hosts directing a guest by voice.

### 4c. Resume / leave-for-hub clarity (MED)

`0.14.0` added the "leave for hub" + idle-sweeper. The 30m/10m thresholds and the "table closed" copy are easy to miss. Suggestions:

- Surface "This room will close in N minutes — anyone still here can keep it open" once we cross 60% of the sweeper window.
- When a player taps **Pick another game** on final results, show a one-time confirmation ("you'll leave the room and can't come back") since this is destructive of the resume row for everyone else.

### 4d. Pre-game lobby chrome (MED)

Watching the host configure things while everyone else stares at a static lobby is a wait state. Cheap wins:

- Animated dot/pulse on the host's name when they're typing into the settings panel.
- Render the "Famous figures drafts" progress per player on Hat (X/6 entered) so the host can see who's holding things up.
- When the host clicks **Start game** with players unready, the current toast disappears quickly. Render a sticky banner naming the not-ready players.

### 4e. Accessibility (MED)

Lightweight scan only — 21 occurrences of `aria-label` / `aria-live` / `role=` across 9 files, but several high-traffic surfaces are missing:

- Turn timer is a number that changes every second — needs `aria-live="off"` with a polite countdown summary at thresholds (10 sec, time up) rather than firing screen-reader spam every tick.
- The QR code is currently decorative — `<QRCode>` should have an explicit `aria-hidden="true"` and the code itself should be the announced/copy target.
- Focus management: when `phase` transitions `lobby → playing`, focus should jump to the new heading; today it stays on the previous (now-hidden) button.
- Confetti has no `prefers-reduced-motion` opt-out. The `confetti-fall` keyframes should bail when the media query matches.

### 4f. Mobile keyboard friction (LOW)

`EnterNamePage` (259 lines, fallow-flagged) has 87-line `handleSubmit` with 18 cyclomatic. From a UX angle:

- Default the name `<input>` to `autoCapitalize="words"` and `enterKeyHint="join"`.
- After join error, focus the input again instead of dumping the user back at the top.

### 4g. Audio cues (LOW)

Tone.js cues are nice but currently every multiplayer screen plays them at full volume with no toggle. Add a one-tap mute control in `GameShell` chrome that writes to `localStorage`. Already adjacent to existing `multiplayerTone` helper.

## 6. Recommended sequence

A pragmatic order, smallest-blast-radius first:

1. **Add the `handle(socket, event, schema, fn)` wrapper** in `socketHandlers.ts`. Pure refactor, eliminates ~120 duplicate lines, and makes 2 and 3 cheaper.
2. **Zod-validate every socket payload** (rides on 1).
3. **Fail-fast CORS in production** + graceful shutdown handler. Small, isolated, ship-worthy independently.
4. **Write `server/roomStore.test.ts` and one Socket.IO integration smoke test.** Adds the safety net before larger refactors.
5. **Refactor `RoomPage.tsx` and `ImposterMultiplayerView.tsx`** into smaller view components. Tests from step 4 protect the move.
6. **Wire fallow into CI** (`fallow:hygiene`, non-blocking at first). Prevents regressions in dupes/dead-code as the refactor progresses.
7. **UX polish**: connection toast, reduced-motion confetti, share API, resume confirmation. Independent and shippable in any order.

Each step is its own version bump per `docs/VERSIONING.md`.
